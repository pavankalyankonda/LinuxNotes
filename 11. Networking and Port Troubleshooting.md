# 11. Networking Basics and Port Troubleshooting


---

## 1. Network Fundamentals

| Concept | Description |
|---|---|
| IP Address | Identifies a device/network interface on an IP network |
| Subnet/CIDR | Defines the network range (e.g., `192.168.1.0/24`) |
| Gateway | Router used to reach destinations outside the local network |
| DNS | Resolves hostnames into IP addresses |
| Port | Identifies the application/service endpoint on a host |
| TCP | Reliable, connection-oriented transport protocol |
| UDP | Connectionless transport protocol |
| Firewall | Controls network traffic based on rules |
| NAT | Translates network addresses, commonly private to public |
| NIC | Network interface card/virtual network interface |

### Private IPv4 ranges

| Range | CIDR |
|---|---|
| 10.0.0.0 – 10.255.255.255 | `10.0.0.0/8` |
| 172.16.0.0 – 172.31.255.255 | `172.16.0.0/12` |
| 192.168.0.0 – 192.168.255.255 | `192.168.0.0/16` |

## 2. Network Interfaces & IP Address

### View IP addresses
```bash
ip addr
ip -br addr
```

### View interfaces and status
```bash
ip link
ip -s link
```

### Check interface details
```bash
ip link show eth0
```

### Loopback
```text
127.0.0.1
```
Used by a machine to communicate with itself.

### Important interface states
- `UP` - Interface is administratively enabled.
- `LOWER_UP` - Underlying link is operational.

### Troubleshooting checklist
- Is the interface present?
- Is it UP?
- Does it have an IP address?
- Is the IP and subnet correct?
- Are packets being dropped or errors increasing?

## 3. Routing & Gateway

Routing determines where packets are sent to reach a destination.

### View routing table
```bash
ip route
```

### Check the route to a specific destination
```bash
ip route get 8.8.8.8
```

### Example routing table
```text
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 proto kernel scope link
```

| Entry | Meaning |
|---|---|
| `default` | Route used when no more specific route exists |
| `via 10.0.1.1` | Gateway |
| `dev eth0` | Network interface |
| `10.0.1.0/24` | Directly connected network |

### Troubleshooting
- Is a route available to the destination?
- Is the correct gateway selected?
- Is the correct interface being used?
- Is traffic going through an unexpected VPN/interface?

## 4. DNS & Name Resolution

DNS resolves hostnames into IP addresses.

```text
google.com → IP address
```

### DNS commands

```bash
# Resolve hostname
nslookup google.com

# Detailed DNS lookup
dig google.com

# Display only IP addresses
dig google.com +short

# Query a specific DNS server
dig @8.8.8.8 google.com

# Resolve using system name resolution
getent hosts google.com
```

### DNS configuration

```bash
# DNS resolver configuration
cat /etc/resolv.conf

# Local hostname mappings
cat /etc/hosts

# Name resolution order
cat /etc/nsswitch.conf

# systemd-resolved status (Ubuntu)
resolvectl status

# Query through system resolver
resolvectl query google.com
```

### Common DNS records

| Record | Purpose |
|---|---|
| A | Hostname to IPv4 |
| AAAA | Hostname to IPv6 |
| CNAME | Alias to another hostname |
| MX | Mail server |
| TXT | Text/verification/SPF records |
| NS | Nameserver |
| PTR | Reverse DNS |

### DNS troubleshooting

```bash
getent hosts hostname
dig hostname
dig @<dns-server-ip> hostname
cat /etc/resolv.conf
resolvectl status
```

If IP connectivity works but hostname resolution fails, investigate DNS.

## 5. Ports & TCP/UDP

An IP identifies a host/interface, while a port identifies the service endpoint.

Example:
```text
10.0.1.10:22  → SSH
10.0.1.10:80  → HTTP
10.0.1.10:443 → HTTPS
```

### Common ports

| Port | Service |
|---|---|
| 20/21 | FTP |
| 22 | SSH |
| 25 | SMTP |
| 53 | DNS |
| 67/68 | DHCP |
| 80 | HTTP |
| 123 | NTP |
| 161 | SNMP |
| 389 | LDAP |
| 443 | HTTPS |
| 445 | SMB |
| 3306 | MySQL |
| 3389 | RDP |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 6443 | Kubernetes API |
| 8080 | Alternate HTTP |
| 8443 | Alternate HTTPS |
| 9090 | Common application/monitoring port |
| 27017 | MongoDB |

### TCP vs UDP

| TCP | UDP |
|---|---|
| Connection-oriented | Connectionless |
| Reliable delivery | No TCP-style delivery guarantee |
| Ordered delivery | No TCP-style ordering guarantee |
| Three-way handshake | No TCP handshake |
| SSH, HTTP/1.1, HTTPS over TCP, DBs | DNS, DHCP, NTP, real-time traffic |

### TCP three-way handshake

```text
Client                 Server
  |------ SYN --------->|
  |<--- SYN + ACK ------|
  |------ ACK --------->|
  |                    |
  | Connection Ready   |
```

## 6. Check Listening Ports & Connections (`ss`)

`ss` is used to inspect listening ports, sockets, and connections.

```bash
# Listening TCP ports
ss -tln

# Listening TCP and UDP ports
ss -tuln

# Show process details
sudo ss -tulpn

# Established TCP connections
ss -tn state established

# Check a specific port
sudo ss -tulpn | grep ':22'
```

### Options

| Option | Meaning |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | Listening |
| `-n` | Numeric output |
| `-p` | Process details |
| `-a` | All sockets |

### Listen addresses

| Address | Meaning |
|---|---|
| `127.0.0.1:8080` | Accessible only through loopback |
| `0.0.0.0:8080` | Listening on all IPv4 interfaces |
| `10.0.1.5:8080` | Listening on a specific interface IP |

A service listening only on `127.0.0.1` may work locally but fail when accessed remotely.

## 7. Connectivity Troubleshooting Tools

### Ping - ICMP reachability

```bash
ping google.com
ping -c 4 8.8.8.8
```

Checks ICMP reachability and round-trip time.

> Ping failure does not always mean the destination is unreachable. ICMP may be blocked.

### Curl - HTTP/HTTPS troubleshooting

```bash
# HTTP/HTTPS request
curl https://example.com

# Response headers only
curl -I https://example.com

# Verbose connection troubleshooting
curl -v https://example.com

# Follow redirects
curl -L https://example.com

# Test a specific IP while preserving hostname
curl --resolve example.com:443:<ip-address> https://example.com
```

Useful for troubleshooting DNS, TCP connectivity, TLS, HTTP response codes, and application endpoints.

### Netcat (`nc`) - Port connectivity

```bash
# Test TCP connectivity
nc -zv <server-ip> 22

# Test application port
nc -zv <server-ip> 8080

# TCP connection test with timeout
nc -zv -w 5 <server-ip> 443
```

### Traceroute - Network path

```bash
traceroute google.com
traceroute <ip-address>
tracepath google.com
```

Identifies intermediate hops along the network path.

Some routers may not respond to traceroute probes. Missing hops do not necessarily indicate failure.

### Tcpdump - Packet capture

```bash
# Capture packets
sudo tcpdump

# Capture on specific interface
sudo tcpdump -i eth0

# Capture traffic on port 443
sudo tcpdump -i eth0 port 443

# Capture traffic from/to a specific host
sudo tcpdump -i eth0 host <ip-address>

# Capture without DNS resolution
sudo tcpdump -n

# Save packet capture
sudo tcpdump -i eth0 -w capture.pcap

# Read saved capture
tcpdump -r capture.pcap
```

## 8. SSH Troubleshooting

SSH uses TCP port 22 by default.

### Connect to server
```bash
ssh username@server-ip
```

### Connect using private key
```bash
ssh -i ~/.ssh/id_rsa username@server-ip
```

### Verbose troubleshooting
```bash
ssh -v username@server-ip
ssh -vvv username@server-ip
```

### Server-side checks
```bash
# SSH service status (Ubuntu)
sudo systemctl status ssh

# Check listening port
sudo ss -tlnp | grep ':22'

# SSH configuration
sudo sshd -t

# Check firewall
sudo ufw status
```

### Common SSH issues

| Error | Possible cause |
|---|---|
| Connection timed out | Firewall, NSG, route, network path |
| Connection refused | SSH service stopped, wrong port, no listener, or active rejection |
| Permission denied | Authentication failure, wrong key, username, permissions |
| Host key verification failed | Host key mismatch or changed server identity |

## 9. Firewall Troubleshooting

Firewalls control incoming and outgoing network traffic.

### UFW commands

```bash
# Check firewall status
sudo ufw status

# Detailed status
sudo ufw status verbose

# List numbered rules
sudo ufw status numbered

# Allow SSH
sudo ufw allow 22/tcp

# Allow HTTP/HTTPS
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Allow a port from a specific IP
sudo ufw allow from 192.168.1.50 to any port 22 proto tcp
```

### Network connection may be blocked at

- Linux firewall (UFW/nftables/iptables)
- Cloud firewall (Azure NSG, AWS Security Group)
- Network firewall
- Route table
- Application itself

> Be careful modifying firewall rules on remote servers. Incorrect rules can block SSH access.

## 10. NAT (Network Address Translation)

NAT translates IP addresses, commonly allowing private IP systems to access external networks.

Example:

```text
Private VM: 10.0.1.4
NAT Public IP: 20.30.40.50
Internet Destination: 8.8.8.8
```

The NAT device translates the source IP/port for outbound communication and maintains connection tracking so return traffic can reach the original client.

Common implementations:

- Azure NAT Gateway
- AWS NAT Gateway
- Firewall SNAT
- Router NAT

Troubleshoot:

- Route to NAT device
- NAT health/configuration
- Firewall rules
- SNAT port exhaustion
- Destination filtering
- Return routing

## 11. MTU Troubleshooting

MTU (Maximum Transmission Unit) defines the maximum packet size that can be transmitted over a link without fragmentation at that layer.

Typical Ethernet MTU:
```text
1500 bytes
```

### Check MTU
```bash
ip link
ip link show eth0
```

### Test packet size (IPv4)
```bash
ping -M do -s 1472 <destination-ip>
```

1472 bytes payload + 28 bytes IPv4/ICMP headers = 1500 bytes.

MTU issues can cause:

- Small packets to work but large packets to fail
- SSH connection to work but file transfers to hang
- TLS/application requests to stall
- VPN/tunnel connectivity problems

## 13. Linux Network Troubleshooting Workflow

Follow this order when a server cannot communicate with another server or application.

### Step 1 - Check interface and IP
```bash
ip -br addr
ip link
```

### Step 2 - Check routes
```bash
ip route
ip route get <destination-ip>
```

### Step 3 - Check IP reachability
```bash
ping -c 4 <destination-ip>
```

### Step 4 - Check DNS
```bash
getent hosts <hostname>
dig <hostname>
```

### Step 5 - Check TCP port connectivity
```bash
nc -zv <destination-ip> <port>
```

### Step 6 - Check the application
```bash
curl -v http://<hostname>:<port>
```

For HTTPS:
```bash
curl -v https://<hostname>
```

### Step 7 - Check listening ports on destination
```bash
sudo ss -tulpn
```

### Step 8 - Check firewall
```bash
sudo ufw status
```

Also check cloud firewall/NSG, routes, and network firewall.

### Step 9 - Trace network path
```bash
traceroute <destination-ip>
```

### Step 10 - Capture packets if required
```bash
sudo tcpdump -i any host <destination-ip>
```

## 14. Common Troubleshooting Scenarios

### Scenario 1: IP works but hostname doesn't

```bash
ping <ip-address>
getent hosts <hostname>
dig <hostname>
```

Likely areas:
- DNS configuration
- DNS record
- Resolver reachability
- `/etc/hosts`

### Scenario 2: Server reachable but application unavailable

```bash
nc -zv <server-ip> <port>
sudo ss -tulpn
curl -v http://<server-ip>:<port>
```

Check:
- Service status
- Listening port
- Bind address
- Firewall
- NSG
- Application logs

### Scenario 3: Connection timed out

```bash
ip route
ip route get <destination-ip>
nc -zv -w 5 <destination-ip> <port>
traceroute <destination-ip>
```

Check:
- Route
- Firewall
- NSG
- Network path
- Destination availability
- Return path

### Scenario 4: Connection refused

```bash
sudo ss -tulpn
sudo systemctl status <service>
```

Check:
- Service running
- Correct port
- Correct bind address
- Firewall rejection
- Whether the destination is actively rejecting the connection

### Scenario 5: HTTP 502 / 504

Check:
- Reverse proxy
- Load balancer
- Backend health
- Backend port
- DNS resolution
- Network connectivity
- Application logs
- Timeout settings

## Basic network information

```bash
hostname                    # Show hostname
ip addr                     # Show interfaces and IP addresses
ip route                    # Show routing table
ip link                     # Show network interfaces and link state
```

`ifconfig` is an older utility and may not be installed by default. Prefer the modern `ip` command.

## Private IP vs public IP

- A **private IP address** is used for communication within private networks and is not directly globally routable.
- A **public IP address** is globally routable on the internet, subject to network configuration and security controls.

```bash
ip addr
curl https://ifconfig.me
```

The second command asks an external service to report the public source IP it sees. Behind NAT, this may be the NAT gateway's public IP rather than an address configured directly on the Linux machine.

## Ports and listening services

An IP address identifies a network interface/host in an IP network. A **port** identifies an application endpoint on a host.

For example, SSH commonly listens on TCP port 22.

Preferred modern command:

```bash
sudo ss -tulpn
```

Legacy alternative (may require installing `net-tools`):

```bash
sudo netstat -tulpn
```

Options:

| Option | Meaning |
|---|---|
| `-t` | TCP sockets |
| `-u` | UDP sockets |
| `-l` | Listening sockets |
| `-p` | Show process information where permitted |
| `-n` | Numeric addresses and ports; do not resolve names |

Other useful commands:

```bash
sudo ss -lntp              # Listening TCP sockets
sudo ss -lunp              # Listening UDP sockets
sudo lsof -i :22           # Processes using port 22 (if lsof is installed)
```

## Test whether a remote port is reachable

```bash
nc -vz 192.168.1.20 22
```

Or, if available:

```bash
telnet 192.168.1.20 22
```

This tests a TCP connection to port 22 on the **remote host**. It does not prove that SSH authentication will succeed; it only tests connectivity to the port.

To test a service on your own machine, use its local address:

```bash
nc -vz 127.0.0.1 22
```

**Important:** Telnet is unencrypted and should not be used to administer servers. It is shown here only as a basic TCP connectivity test. Prefer `nc` for this purpose.

## Apache web server

Apache HTTP Server is web-server software that listens for HTTP/HTTPS requests and serves web content.

- Ubuntu/Debian package and service name: commonly `apache2`
- RHEL-family package and service name: commonly `httpd`

They are distribution-specific packaging/service conventions for the same Apache HTTP Server project.

Ubuntu examples:

```bash
sudo apt install apache2
sudo systemctl status apache2
sudo systemctl enable --now apache2
```
