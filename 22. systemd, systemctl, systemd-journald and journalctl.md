# **22. systemd, systemctl, systemd-journald and journalctl**

## **22.1 What is systemd?**

`systemd` is a **system and service manager** used by most modern Linux distributions, including Ubuntu.

It is responsible for bringing the Linux system into a usable state after the kernel has initialized. It manages services, background processes, mounts, sockets, timers, dependencies, and other system resources.

In most modern Linux distributions, `systemd` runs as **PID 1**, the first userspace process started by the Linux kernel.

```
ps -p 1 -f
```

Example output:

```
UID    PID  PPID  C STIME TTY   TIME CMD
root     1     0   0 ...         /sbin/init
```

On a system using systemd, `/sbin/init` may be a symbolic link to systemd.

Check it using:

```
ls -l /sbin/init
```

Or:

```
systemctl --version
```

The important concept:

The Linux kernel initializes hardware and core functionality, then starts the initial userspace process (`systemd`). systemd then manages the services and processes required to bring the operating system into its operational state.

## **22.2 Linux Boot Process and the Role of systemd**

To understand systemd, first understand what happens when a Linux machine starts.

## **Linux Boot Flow**

**1. BIOS / UEFI**

Hardware initialization

**2. Bootloader (GRUB)**

Loads Linux kernel and initramfs

**3. Linux Kernel**

Initializes CPU, memory, drivers and core subsystems

**4. systemd (PID 1)**

Initial userspace process and system manager

**5. systemd starts required units**

Networking, SSH, mounts, services and other resources

**6. System reaches its target**

Multi-user mode, graphical mode or other configured state

## **22.3 What is PID 1?**

PID stands for Process ID.

Every running process in Linux is assigned a process ID. PID 1 is the first userspace process started by the kernel and has a special role in the system.

On most modern Linux systems using systemd:

```
PID 1 = systemd
```

Check PID 1:

```
ps -p 1 -o pid,ppid,comm,args
```

Example:

```
 PID  PPID COMMAND  COMMAND
   1     0 systemd /sbin/init
```

### **Why is PID 1 important?**

PID 1 is responsible for managing the userspace system and plays a central role in process lifecycle management.

systemd:

- Starts system services.
- Manages service dependencies.
- Monitors service states.
- Handles service restart policies.
- Coordinates system shutdown and reboot.
- Manages resources through cgroups.
- Can collect logs through journald.

For example, when you start an SSH service:

```
sudo systemctl start ssh
```

systemd is responsible for starting and managing the SSH service according to its configuration.

## **22.4 What are systemd Units?**

systemd manages resources through objects called **units**.

A unit is a configuration and management object that tells systemd what to manage and how.

Different unit types are used for different purposes.

| Unit type | Extension    | Purpose                                                  | Example              |
| --------- | ------------ | -------------------------------------------------------- | -------------------- |
| Service   | `.service`   | Manages a service or process                             | `ssh.service`        |
| Socket    | `.socket`    | Manages a socket for communication or activation         | `docker.socket`      |
| Target    | `.target`    | Groups units into a desired system state                 | `multi-user.target`  |
| Mount     | `.mount`     | Manages filesystem mount points                          | `mnt-data.mount`     |
| Automount | `.automount` | Automatically triggers a mount when accessed             | `mnt-data.automount` |
| Timer     | `.timer`     | Schedules a unit to run at a particular time or interval | `backup.timer`       |
| Path      | `.path`      | Monitors filesystem paths for changes                    | `watch-folder.path`  |
| Slice     | `.slice`     | Organizes processes into resource groups                 | `system.slice`       |
| Scope     | `.scope`     | Tracks processes started externally                      | `user.slice`         |

### **Example of units on a Linux server**

```
systemctl list-units --type=service
```

Examples:

```
ssh.service
cron.service
systemd-journald.service
docker.service
```

Each of these represents a service unit managed by systemd.

## **22.5 What is a systemd Service?**

A service unit is used to manage a background process or application.

Examples:

- SSH server
- Nginx
- Docker
- Database services
- Monitoring agents
- Custom applications

A service unit typically defines:

- What command should run.
- When the service should start.
- Which dependencies it requires.
- What user it should run as.
- Whether it should restart after failure.
- Where its logs are handled.

Example:

```
systemctl status ssh
```

This command asks systemd for the current state of the SSH service.

## **22.6 systemctl**

`systemctl` is the command-line utility used to interact with systemd.

It allows administrators to:

- Start services.
- Stop services.
- Restart services.
- Reload service configurations.
- Enable services at boot.
- Disable services at boot.
- Check service status.
- Inspect dependencies.
- Manage targets.

### **Basic syntax**

```
systemctl [OPTIONS] COMMAND [UNIT]
```

### **Service management commands**

| Command                            | Purpose                                                                      |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| `systemctl status ssh`             | Display service status and recent log messages                               |
| `sudo systemctl start ssh`         | Start a service now                                                          |
| `sudo systemctl stop ssh`          | Stop a service now                                                           |
| `sudo systemctl restart ssh`       | Stop and start the service again                                             |
| `sudo systemctl reload ssh`        | Ask the service to reload configuration without a full restart, if supported |
| `sudo systemctl enable ssh`        | Configure the service to start automatically at boot                         |
| `sudo systemctl disable ssh`       | Remove its automatic startup configuration                                   |
| `sudo systemctl enable --now ssh`  | Enable and start the service                                                 |
| `sudo systemctl disable --now ssh` | Disable and stop the service                                                 |
| `systemctl is-active ssh`          | Check whether the service is active                                          |
| `systemctl is-enabled ssh`         | Check whether it is enabled at boot                                          |

`start` and `enable` are different.

- `start` → Starts the service now.
- `enable` → Configures it to start automatically during future boots.
- `enable --now` → Enables it and starts it immediately.

### **Example**

```
sudo systemctl start nginx
```

Nginx starts now but may not automatically start after a reboot.

```
sudo systemctl enable nginx
```

Nginx is configured to start automatically during boot but is not necessarily started immediately.

```
sudo systemctl enable --now nginx
```

Nginx is configured to start at boot and is started immediately.

## **22.7 systemctl status — Understanding the output**

Command:

```
systemctl status ssh
```

Example output:

```
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; enabled)
     Active: active (running) since ...
       Docs: man:sshd(8)
             man:sshd_config(5)
   Main PID: 1224 (sshd)
      Tasks: 1
     Memory: 2.1M
        CPU: 25ms
```

### **Important fields**

| Field      | Meaning                                        |
| ---------- | ---------------------------------------------- |
| `Loaded`   | Whether the unit file was found and loaded     |
| `enabled`  | Whether it is configured for automatic startup |
| `disabled` | Not configured for automatic startup           |
| `Active`   | Current service state                          |
| `Main PID` | Main process associated with the service       |
| `Tasks`    | Number of tasks/processes tracked for the unit |
| `Memory`   | Memory usage attributed to the unit            |
| `CPU`      | CPU time consumed                              |
| `Docs`     | Documentation references                       |

### **Common service states**

| State              | Meaning                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `active (running)` | Service is running                                                                       |
| `active (exited)`  | Service successfully completed its start action and is not necessarily running a process |
| `active (waiting)` | Service is active and waiting for an event                                               |
| `inactive`         | Service is not currently active                                                          |
| `failed`           | Service failed to start or encountered a failure                                         |
| `activating`       | Service is in the process of starting                                                    |
| `deactivating`     | Service is in the process of stopping                                                    |

Note: `active (exited)` is not always an error. Some one-shot services perform an operation, exit successfully, and remain considered active.

## **22.8 systemd-journald**

`systemd-journald` is the logging service in the systemd ecosystem.

It collects and stores log messages from sources such as:

- The Linux kernel.
- systemd services.
- Applications using the journal interface.
- Standard output and standard error streams of services managed by systemd.
- Other logging sources configured on the system.

Check its status:

```
systemctl status systemd-journald
```

### **Journal storage locations**

Common locations

```
/var/log/journal/
/run/log/journal/
```

| Directory           | Purpose                                                                  |
| ------------------- | ------------------------------------------------------------------------ |
| `/var/log/journal/` | Persistent journal storage across reboots, when configured and available |
| `/run/log/journal/` | Runtime journal storage; typically cleared after reboot                  |

The actual storage behavior depends on the journald configuration and the distribution.

### **Check journald configuration**

```
cat /etc/systemd/journald.conf
```

Additional configuration may exist in:

```
/etc/systemd/journald.conf.d/
```

Common configuration settings include:

| Setting                 | Purpose                                                     |
| ----------------------- | ----------------------------------------------------------- |
| `Storage=`              | Controls journal storage mode                               |
| `SystemMaxUse=`         | Limits disk space used by journal files                     |
| `SystemKeepFree=`       | Controls how much disk space journald attempts to keep free |
| `MaxRetentionSec=`      | Controls journal retention time                             |
| `Compress=`             | Controls compression                                        |
| `ForwardToSyslog=`      | Controls forwarding to syslog                               |
| `RateLimitIntervalSec=` | Controls log rate-limiting interval                         |
| `RateLimitBurst=`       | Controls permitted burst of log messages                    |

### **Storage options**

| Value        | Behavior                                                              |
| ------------ | --------------------------------------------------------------------- |
| `volatile`   | Store journal in runtime storage                                      |
| `persistent` | Store journal on disk under `/var/log/journal/`                       |
| `auto`       | Persistent if `/var/log/journal/` exists; otherwise volatile          |
| `none`       | Do not store journal data locally; forwarding may still be configured |

### **Why journald is important**

In a production environment, a service may fail, crash, restart repeatedly, or encounter an unexpected error.

journald helps collect the information needed to investigate:

- Service startup failures.
- Application errors.
- Kernel errors.
- Boot problems.
- Authentication-related events.
- Out-of-memory events.
- Network or disk-related issues.

## **22.9 journalctl**

`journalctl` is the command-line utility used to read, filter, search, and monitor logs stored by `systemd-journald`.

### **Basic commands**

| Command                           | Purpose                                      |
| --------------------------------- | -------------------------------------------- |
| `journalctl`                      | Show journal entries                         |
| `journalctl -u ssh`               | Show logs for SSH unit                       |
| `journalctl -u ssh -n 10`         | Show last 10 entries for SSH                 |
| `journalctl -u ssh -f`            | Follow SSH logs live                         |
| `journalctl -b`                   | Show logs from current boot                  |
| `journalctl -b -1`                | Show logs from previous boot                 |
| `journalctl -k`                   | Show kernel messages                         |
| `journalctl --since today`        | Show logs since today                        |
| `journalctl --since "1 hour ago"` | Show logs from the last hour                 |
| `journalctl -p err`               | Show error priority and more severe messages |
| `journalctl -xe`                  | Show recent entries with explanatory details |
| `journalctl --disk-usage`         | Show journal disk usage                      |

With `sudo`, you may be able to read logs that are not accessible to your normal user.

```
sudo journalctl -u ssh -n 50
```

### **Filter by service**

```
journalctl -u nginx
```

### **Filter by time**

```
journalctl --since "2026-11-22 14:00:00"
```

```
journalctl --since "2026-11-22 14:00:00" --until "2026-11-22 15:00:00"
```

### **Filter by priority**

```
journalctl -p err
```

### **Priority levels**

| Priority | Name          | Meaning                       |
| -------- | ------------- | ----------------------------- |
| 0        | Emergency     | System unusable               |
| 1        | Alert         | Immediate action required     |
| 2        | Critical      | Critical conditions           |
| 3        | Error         | Error conditions              |
| 4        | Warning       | Warning conditions            |
| 5        | Notice        | Normal but significant events |
| 6        | Informational | Informational messages        |
| 7        | Debug         | Debugging messages            |

For example:

```
journalctl -p warning
```

Shows warning-level messages and more severe priorities.

```
journalctl -p err
```

Shows error-level messages and more severe priorities.

## **22.11 systemctl vs journalctl**

These two commands are commonly used together during Linux troubleshooting, but they serve different purposes.

| Tool               | Main purpose                             | Example                |
| ------------------ | ---------------------------------------- | ---------------------- |
| `systemd`          | System and service manager               | PID 1                  |
| `systemctl`        | Inspect and control systemd units        | `systemctl status ssh` |
| `systemd-journald` | Collects and stores journal logs         | Logging daemon         |
| `journalctl`       | Reads, filters and monitors journal logs | `journalctl -u ssh`    |

### **Relationship between them**

**systemd — System Manager**

PID 1 • Boot • Units • Dependencies • Process lifecycle

**systemctl**

Control & inspect

Start, stop, restart, enable, status, inspect

**systemd-journald**

Collect & store logs

Service output, kernel messages, system logs

**journalctl**

Read, search, filter and follow logs to understand what happened

### **Easy way to remember**

- `systemctl` → **What is the service doing? Can I control it?**
- `journalctl` → **What happened? Why did it fail? What do the logs say?**

## **22.12 Practical Troubleshooting — Service Not Working**

Imagine that you are working on a Linux server and your SSH, Docker, Nginx, or any other service is not working.

The recommended approach is to check the service state first and then investigate the logs.

### **Step 1: Check the service status**

```
sudo systemctl status nginx
```

Check:

- Is the service active?
- Is it failed?
- What is the main PID?
- Is there an error message?
- Is the service restarting repeatedly?

### **Step 2: Check the logs**

```
sudo journalctl -u nginx -n 50
```

Look for:

- Configuration errors.
- Port conflicts.
- Permission denied.
- Missing files.
- Connection failures.
- Application crashes.

### **Step 3: Check logs from the current boot**

```
sudo journalctl -u nginx -b
```

### **Step 4: Validate the service configuration**

For Nginx:

```
sudo nginx -t
```

For SSH:

```
sudo sshd -t
```

Whenever possible, validate the configuration before restarting a production service.

### **Step 5: Check processes**

```
ps -ef | grep nginx
```

Or:

```
pgrep -a nginx
```

### **Step 6: Check listening ports**

```
sudo ss -tulpn
```

For a particular port:

```
sudo ss -tulpn | grep ':80'
```

### **Step 7: Restart only when appropriate**

```
sudo systemctl restart nginx
```

### **Step 8: Verify**

```
sudo systemctl status nginx
```

And check logs again:

```
sudo journalctl -u nginx -n 50
```

**Production troubleshooting mindset**

Do not immediately restart a failed service without checking logs.

First identify what happened. A restart may temporarily fix the symptom while hiding the root cause, or cause further disruption.

## **22.14 Managing Journal Disk Space**

On production Linux servers, logs can consume disk space if not controlled properly.

### **Check journal disk usage**

```
sudo journalctl --disk-usage
```

### **Remove old journal entries based on size**

```
sudo journalctl --vacuum-size=500M
```

Keeps the journal within approximately 500 MB by removing older journal files as needed.

### **Remove journal files older than a specified duration**

```
sudo journalctl --vacuum-time=7d
```

Removes archived journal files older than 7 days.

### **Remove archived journal files until they fit within a limit**

```
sudo journalctl --vacuum-size=1G
```

Vacuum operations remove archived journal files. Active journal files may not be removed until they are archived.

For production systems, it is generally better to configure journal retention and storage limits in `journald` rather than repeatedly deleting logs manually.

## **22.15 Common Mistakes and Differences**

| Mistake                                            | Correct understanding                                                                    |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `start` and `enable` are the same                  | `start` runs now; `enable` configures automatic startup                                  |
| `restart` and `reload` are the same                | `restart` restarts the process; `reload` asks it to reload configuration if supported    |
| `After=` starts the dependency                     | `After=` only establishes ordering                                                       |
| `Requires=` guarantees the dependency starts first | It establishes a dependency, but startup ordering must be defined separately when needed |
| `active` means the application is fully functional | systemd may report active while the application has a problem at its own level           |
| `active (exited)` always means failure             | Many one-shot services complete successfully and remain active in this state             |
| `systemctl status` provides all logs               | It shows limited recent logs; `journalctl` provides better filtering and investigation   |
| `enable` starts the service immediately            | It generally configures boot-time startup; use `--now` for both                          |
| `daemon-reload` restarts every service             | It reloads systemd's unit configuration, not all running services                        |
| `journalctl` manages services                      | It is a log-reading tool, not a service control tool                                     |

## **22.16 Real-World Example: SSH Service Troubleshooting**

Imagine you try connecting to your Azure Linux VM using SSH, but the connection fails.

### **Check the SSH service**

```
sudo systemctl status ssh
```

If you see:

```
Active: failed
```

Investigate the logs:

```
sudo journalctl -u ssh -n 100
```

If the service is running, check whether SSH is listening:

```
sudo ss -tulpn | grep ':22'
```

Validate the configuration:

```
sudo sshd -t
```

Check the service configuration:

```
sudo systemctl cat ssh
```

Check whether it is configured to start at boot:

```
systemctl is-enabled ssh
```

If you have identified and fixed the issue, start or restart the service:

```
sudo systemctl restart ssh
```

Verify:

```
systemctl status ssh
```

Follow live logs while testing a connection:

```
sudo journalctl -u ssh -f
```

This is particularly useful when you attempt to connect from your Windows machine while watching the Linux VM's logs.

systemctl status nginx

When you boot a Linux server:

```
Linux Kernel
     |
     v
Starts PID 1
     |
     v
systemd
     |
     +---- Manages Services
     |       |
     |       +---- SSH
     |       +---- Docker
     |       +---- Nginx
     |       +---- Cron
     |
     +---- Manages Targets
     |
     +---- Manages Mounts
     |
     +---- Manages Timers
     |
     +---- Manages Dependencies
     |
     +---- Manages Process Lifecycle
     |
     +---- Works with systemd-journald
                 |
                 +---- Collects logs
                 |
                 +---- Stores journal entries
                             |
                             v
                        journalctl
                             |
                             v
                   Administrator investigates
```

### **Remember these four components**

# **systemd**

The manager

Boots and manages the system, services, dependencies and resources.

# **systemctl**

The control tool

Used to inspect, start, stop, restart and enable units.

# **journald**

The logger

Collects and stores system and service logs.

# **journalctl**

The log reader

Used to search, filter, monitor and investigate logs.

> **In Linux administration, systemctl tells you the state of a service and allows you to control it. journalctl helps you understand what happened inside the system or service. systemd is the manager behind these operations.**

This structure should make your Linux notes much more useful for interviews, daily administration, and real-world DevOps troubleshooting.
