# **Linux Logging & Troubleshooting Guide**

Linux logging is essential for identifying why a server, service, application, or hardware component is failing.

For DevOps and Linux administration, you should understand **where Linux stores logs, how to read them, and which logs to check for different problems.**

## **1. How does Linux handle logging?**

Linux logging can be understood through two main approaches:

## **Linux Logging**

**1. Systemd Journal Logging**

journalctl

- Managed by `systemd-journald`.
- Collects logs from services, kernel, system processes and applications.
- Stores logs in a structured journal format.

**2. Traditional File-Based Logging**

/var/log

- Logs stored in normal text files.
- Commonly managed by `rsyslog` or other logging services.
- Applications may also write directly to their own log files.

**Important:** These are not completely separate systems. They can work together. For example, `systemd-journald` can collect a message and forward it to `rsyslog`, which may write it into `/var/log/syslog`.

Also, `dmesg` is a command to read kernel messages, not a third logging system.

## **2. Understand the logging architecture**

A simplified view of how logs flow:

**Linux system activity**

Services · Kernel · SSH · Applications · System processes

**systemd-journald**

Collects and stores journal messages

**Journal storage**

journalctl

/var/log/journal

**Traditional logs**

rsyslog

/var/log/\*.log

Not every message follows this exact path. Applications can write directly to log files, and some services send messages straight to the journal.

## **3. Systemd Journal Logging**

### **What is systemd-journald?**

`systemd-journald` is a system service responsible for collecting and storing logs.

It collects information from:

- System services such as SSH, Docker and Nginx.
- Kernel messages.
- System startup and shutdown.
- Standard output and error from services.
- Other system processes.

### **Where are journal logs stored?**

| Location            | Purpose                                             |
| ------------------- | --------------------------------------------------- |
| `/run/log/journal/` | Volatile journal storage; usually cleared on reboot |
| `/var/log/journal/` | Persistent journal storage, when enabled            |

Check journal storage:

```
journalctl --disk-usage
```

Check whether persistent journal storage exists:

```
ls -ld /var/log/journal
```

### **Important journalctl commands**

```
journalctl                  # All available journal logs
journalctl -f               # Monitor logs live
journalctl -n 50            # Last 50 entries
journalctl -xe              # Recent logs with explanations
journalctl -u nginx         # Nginx service logs
journalctl -xeu nginx       # Troubleshoot Nginx
journalctl -p err           # Errors and more severe messages
journalctl -b               # Current boot logs
journalctl -b -1            # Previous boot logs
journalctl -k               # Kernel logs
journalctl --since today    # Logs since today
journalctl --since "1 hour ago"
```

### **Understand journalctl options**

| Option    | Meaning                                            |
| --------- | -------------------------------------------------- |
| `-x`      | Show additional explanatory messages, if available |
| `-e`      | Jump to the end of the logs                        |
| `-u`      | Filter by service/unit                             |
| `-f`      | Follow logs live                                   |
| `-n`      | Show the last N entries                            |
| `-p`      | Filter by priority                                 |
| `-b`      | Filter by boot                                     |
| `-k`      | Show kernel messages                               |
| `--since` | Logs after a specified time                        |
| `--until` | Logs before a specified time                       |

Example:

```
sudo journalctl -xeu ssh
```

Meaning:

- `-x`: Additional explanatory information.
- `-e`: Jump to the latest entries.
- `-u ssh`: Show SSH service logs.

## **4. Traditional logging – /var/log**

`/var/log` is the standard directory for traditional Linux log files.

These files are usually readable using commands such as:

```
cat
less
grep
tail
```

List available logs:

```
ls -lh /var/log/
```

### **Important log files**

Common Ubuntu/Debian locations; other distributions may use different files.

| Log file                    | Purpose                                             |
| --------------------------- | --------------------------------------------------- |
| `/var/log/syslog`           | General system messages                             |
| `/var/log/auth.log`         | SSH, sudo and authentication events                 |
| `/var/log/kern.log`         | Kernel-related messages                             |
| `/var/log/dmesg`            | Boot-time kernel message snapshot, where configured |
| `/var/log/dpkg.log`         | Package installation, upgrade and removal           |
| `/var/log/boot.log`         | Boot-related messages, where configured             |
| `/var/log/cron`             | Cron job logs, where configured                     |
| `/var/log/alternatives.log` | System alternatives changes                         |

On RHEL-based systems, common alternatives include:

| Ubuntu/Debian       | RHEL/Rocky/AlmaLinux                         |
| ------------------- | -------------------------------------------- |
| `/var/log/syslog`   | `/var/log/messages`                          |
| `/var/log/auth.log` | `/var/log/secure`                            |
| `/var/log/kern.log` | Kernel messages often in `/var/log/messages` |

**Important:** Files such as `syslog`, `auth.log`, and `kern.log` depend on the logging configuration. They may not exist on systems that rely primarily on the journal.

### **Useful commands**

```
sudo less /var/log/syslog
sudo tail -50 /var/log/syslog
sudo tail -f /var/log/syslog
sudo grep -i error /var/log/syslog
sudo grep -i failed /var/log/auth.log
```

## **5. Kernel logging – dmesg and journalctl -k**

The Linux kernel generates messages related to hardware and low-level system operations.

Examples:

- Disk errors.
- Driver failures.
- USB device issues.
- Memory exhaustion (OOM).
- Hardware detection.
- Filesystem errors.

### **What is dmesg?**

`dmesg` displays messages from the kernel's ring buffer.

```
dmesg
dmesg -T
dmesg -T | tail -50
dmesg -T | grep -i error
dmesg -T | grep -i oom
```

### **dmesg vs journalctl -k**

| Command         | Purpose                                     |
| --------------- | ------------------------------------------- |
| `dmesg`         | Reads kernel ring-buffer messages           |
| `journalctl -k` | Reads kernel messages stored in the journal |

For troubleshooting previous boots, `journalctl -k -b -1` can be particularly useful if those logs were retained.

## **6. Login and authentication records**

Linux also maintains special binary files to record login activity.

These are not ordinary text logs.

| File   | Meaning                         | Command    |
| ------ | ------------------------------- | ---------- |
| `utmp` | Currently logged-in sessions    | `who`, `w` |
| `wtmp` | Historical login/logout records | `last`     |
| `btmp` | Failed login attempts           | `lastb`    |

Common locations:

```
/run/utmp
/var/log/wtmp
/var/log/btmp
```

Useful commands:

```
who                 # Current logged-in users
w                   # Users and their activity
last                # Previous login history
last reboot         # Reboot history
sudo lastb          # Failed login attempts
```

## **7. Application logging**

Applications often maintain their own logs under `/var/log`.

For example:

| Application         | Log directory                        |
| ------------------- | ------------------------------------ |
| Apache (Ubuntu)     | `/var/log/apache2/`                  |
| Apache (RHEL)       | `/var/log/httpd/`                    |
| Nginx               | `/var/log/nginx/`                    |
| MySQL               | Depends on configuration             |
| Custom applications | Depends on application configuration |

### **Nginx example**

```
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log
```

- `access.log` → Requests received by Nginx.
- `error.log` → Nginx errors and warnings.

## **8. Troubleshooting decision table**

This is the most important section to remember during real-time production support.

| Problem                    | First command to run                       |
| -------------------------- | ------------------------------------------ |
| Service failed to start    | `systemctl status nginx`                   |
| Why did the service fail?  | `journalctl -xeu nginx`                    |
| Recent system errors       | `journalctl -p err -b`                     |
| Previous reboot issue      | `journalctl -b -1`                         |
| Kernel or disk issue       | `journalctl -k`                            |
| OOM / memory issue         | `journalctl -k \\| grep -i oom`            |
| SSH login failure          | `journalctl -u ssh` or check `auth.log`    |
| Sudo issue                 | `grep sudo /var/log/auth.log`              |
| Who is logged in now?      | `who` or `w`                               |
| Who logged in previously?  | `last`                                     |
| Failed login attempts      | `sudo lastb`                               |
| Nginx application issue    | `tail -f /var/log/nginx/error.log`         |
| General system issue       | `journalctl -xe` or `less /var/log/syslog` |
| Watch a service issue live | `journalctl -fu nginx`                     |

## **9. Production troubleshooting workflow**

Suppose a user reports that Nginx is not working on a Linux server.

Follow this order:

1. **Check service status**
   ```
   sudo systemctl status nginx
   ```
   Confirm whether the service is running, failed, or inactive.
2. **Check service logs**
   ```
   sudo journalctl -xeu nginx
   ```
   Identify the error message and failure reason.
3. **Check configuration**
   ```
   sudo nginx -t
   ```
   Validate the Nginx configuration.
4. **Check ports**
   ```
   sudo ss -tulpn
   ```
   Check whether another process is using port 80 or 443.
5. **Check application logs**
   ```
   sudo tail -50 /var/log/nginx/error.log
   ```
   Look for application-specific errors.
6. **Monitor after fixing**
   ```
   sudo journalctl -fu nginx
   ```
   Confirm whether new errors occur after restarting the service.
