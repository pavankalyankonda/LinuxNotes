# 10. Process Management and Signals

## 10.1 Inspect processes

```bash
ps -ef                         # List processes in full-format output
ps aux                         # Another widely used process listing format
ps -p 1                         # Inspect PID 1
ps -p 1234 -o pid,ppid,stat,cmd # Inspect a particular process
pgrep -a sshd                   # Find processes by name
top                             # Interactive process and resource monitor
```

In `ps -ef`:

- `UID` = user running the process
- `PID` = process ID
- `PPID` = parent process ID
- `C` = processor utilization field
- `STIME` = start time
- `TTY` = controlling terminal, if any
- `TIME` = accumulated CPU time
- `CMD` = command

On a typical system, PID 1 is the init/service manager (often systemd). Linux also has kernel threads; `kthreadd` is commonly PID 2. Do not assume all processes are direct children of PID 1 or PID 2.

## 10.2 Stop a service correctly

If a process is managed by systemd, prefer controlling its service:

```bash
sudo systemctl stop ssh
sudo systemctl status ssh
```

Stopping a service through systemd lets the service manager perform its configured stop procedure.

## 10.3 `kill` and signals

`kill` sends a signal to a process. It does not always mean immediate termination.

```bash
kill 1234          # Send SIGTERM (default): request graceful termination
kill -15 1234      # Explicit SIGTERM
kill -9 1234       # Send SIGKILL: force termination
```

- **SIGTERM (15):** Gives the process a chance to clean up and exit.
- **SIGKILL (9):** Cannot be caught or ignored; the process cannot perform normal cleanup.

**Best practice:** Try normal service management or SIGTERM first. Use `kill -9` only when necessary, because it can leave temporary files, locks or incomplete work.

Inspect available signals:

```bash
kill -l
```
